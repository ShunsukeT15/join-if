# 条件付き出欠アンケート「ひみつ出欠」設計書

Nov 15, 2026 · @SHUNSUKE

## 1. 背景と目的

「ひみつ出欠」は、誰が何と答えたかを招待側に見せずに、条件付きの参加意向まで集めて最終的な出席者だけを出すWebサービスです（名称は仮）。

**背景**

- 結婚式に呼ぶ人を決めるとき、問題は人数制限ではなく「誰が来たいか」です。
- 参加意向は行く／行かないの二択ではありません。「Aさんが来るなら行く」のように、他の人の出欠次第で決まる人がいます。
- 招待側に直接答えると、断りづらさや人間関係への配慮から本音が出にくくなります。
- 調整さんや Walica のような既存サービスには、条件付きの回答を匿名で集めて組み合わせを計算する機能がありません。

**目的**

1. 回答者が気兼ねなく本音で答えられるようにする。個別の回答は招待側にも他の回答者にも見せない。
2. 条件付きの回答を、条件を守りつつ参加者が最大になるように自動で組み合わせる。
3. 誰でもルームを作って使えるようにする。結婚式に限らず、同窓会や旅行などグループの集まり全般に使える。

## 2. 前提と信頼モデル

信頼するのは運用者（開発者本人）だけです。その他の利用者には、画面とAPIで必要なものしか見せません。

| 立場 | 信頼 | 見られるもの | 想定するリスク |
| --- | --- | --- | --- |
| 運用者（開発者） | する。回答を見ないと約束する | データベースの全データ | 内部の不正は想定しない。誤って目に入ることは運用ルールで避ける |
| 招待側（ルーム作成者） | しない | メンバー一覧、回答済み／未回答、未使用の招待URL、最終結果 | 好奇心から中身を探る。招待URLを先に開いて本人になりすます |
| 回答者（メンバー） | しない | 上記（招待URLを除く）に加え、自分の回答内容 | 他人の招待URL・専用URLを使って成りすます |
| URLを知った第三者 | しない | そのURLの持ち主と同じもの | URLの転送・漏えい |
| すべての利用者 | しない | — | API に送る値を書き換えて、権限外の操作や他ルームへの操作を試みる |

**方針**

- 招待側も回答者も結果を操作して得をすることがないため、不正は「防ぐ」より「本人が気づける」ことを重視します。
- アカウント登録はしません。本人の確認は推測できないURLで行います。招待側が送る招待URLは1回限りで、本人が開いた時点で招待側も知らない専用URLに切り替わります。招待側が先に開けば本人が「使用済み」として気づけます。
- 暗号化による「運用者にも見えない」仕組みは今回は採用しません。運用者を信頼する前提だからです。将来の拡張として未決事項に残します。
- 最終結果から個人の回答がある程度推測できてしまうことは許容します。いずれ分かる情報だからです。ただし「行かない」と「条件が合わず不参加」は、どの画面でも区別しません。

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| ルーム | 1つのイベントの出欠確認の単位。招待側が作る |
| 招待側 | ルームを作り、メンバーを登録して締め切る人。メンバーではない |
| メンバー | 招待されて回答する人 |
| 管理用URL | 招待側だけが持つ、ルームを操作するためのURL |
| 招待URL | 招待側がメンバーに送る、**1回しか使えない**URL。開くと専用URLに切り替わり、以後は無効になる |
| 専用URL | 招待URLを開いた本人にだけ発行される回答用のURL。招待側も知らない |
| 有効化 | 招待URLを開いて専用URLを受け取ること |
| 再発行 | 招待側が新しい招待URLを作ること。そのメンバーの専用URLと回答は無効・削除になる |
| 回答 | 「行く」「行かない」「条件付きで行く」のいずれか。条件付きなら条件も含む |
| 人物条件 | 「選んだ人のうちN人以上が来るなら」という条件 |
| 人数条件 | 「自分以外の参加者が全体でM人以上なら」という条件 |
| 締め切り | 回答の受付を止めて集計する操作。招待側が行う |
| 最終結果 | 集計で決まった「参加」と「不参加」の一覧。理由は含まない |
| 操作記録 | 回答の保存や再発行などを、内容を含めず日時だけ残す記録 |

| F-15 | 締め切り後も受付を再開できる。再開すると結果は非表示になり、回答は残る | 招待側 |

| 分類 | 要件 |

| 秘匿性 | 招待側が知り得るURL（管理用URL・招待URL）では、本人の回答内容を見られない |
| 秘匿性 | 「行かない」と「条件が合わず不参加」を、画面でもAPIでも区別しない |
| 権限 | すべての操作で、トークンの種類・対象のルーム・対象のメンバーをサーバーで確かめる。詳細は 8.6 |
| 改竄防止 | 最終結果、更新日時、操作記録はサーバーだけが書き込む。利用者が送った値では書き換わらない |
| 認証 | 管理用・招待・専用の各URLには、推測できない乱数トークン（128ビット以上）を使う |

| データ保持 | 締め切りから90日後に、ルームと回答と操作記録を自動で削除する |
| 防御 | ルーム作成、有効化、回答保存には、接続元ごとの回数制限をかける |

### 4.3 スコープ外（MVPではやらないこと）

- 「この人が来るなら行かない」のような否定の条件。参加者が最大の組み合わせが1つに決まらなくなるためです。
- 「(AかつB) または C」のような複数の条件の組み合わせ
- アカウント登録、メールやLINEへの自動通知
- 座席表、引き出物、会費の管理
- 運用者にも回答を見せない暗号化

## 5. 機能仕様

画面は5つです。ルームには「受付中」と「締切済み」の2つの状態があり、表示内容は状態と立場で決まります。

### 5.1 画面一覧

| 画面 | URL | 使う人 | 主な内容 |
| --- | --- | --- | --- |
| トップ | `/` | 誰でも | サービスの説明、ルーム作成フォーム（イベント名・締切・メッセージ） |
| 管理 | `/r/{roomId}/admin#{adminToken}` | 招待側 | 設定の変更、メンバーの追加・削除・招待URLの再発行、回答状況、締め切り・再開、最終結果 |
| 招待 | `/r/{roomId}/i#{inviteToken}` | メンバー | 招待URLを有効化して専用URLに移動する。使用済みならその案内 |
| 回答 | `/r/{roomId}/m#{memberToken}` | メンバー | イベント情報、回答フォーム、自分の回答状況（最終更新日時・保存回数・有効化日時）、メンバーの回答状況、最終結果 |
| エラー | — | 誰でも | トークンが無効・削除済みの場合の案内 |

トークンは URL の `#` 以降に置きます。`#` 以降はサーバーのアクセスログやリファラーに残らないためです。画面の JavaScript が読み取り、API のリクエストヘッダーで送ります。

### 5.2 主な流れ

1. 招待側がトップでルームを作る。管理用URLが表示され、「このURLを保存してください」と案内する。
2. 招待側がメンバーを名前で追加する。一人ずつ招待URLが発行される。
3. 招待側が「案内文をコピー」で招待URLを各自に送る。
4. メンバーが招待URLを開く。サーバーが専用URLを発行して回答画面に移り、「このURLをブックマークしてください」と案内する。招待URLは以後使えない。
5. メンバーが回答して保存する。締め切りまでは何度でも変更できる。
6. 招待側が「締め切って結果を出す」を押す。未回答の人数を表示して確認してから実行する。
7. サーバーが集計し、全員の画面に最終結果が表示される。
8. 必要なら招待側が受付を再開する。結果は非表示になり、手順 5 に戻る。

### 5.3 表示ルール

| 表示するもの | 招待側 | メンバー本人 | 他のメンバー |
| --- | --- | --- | --- |
| イベント名・締切・メッセージ | 表示 | 表示 | 表示 |
| メンバーの名前一覧 | 表示 | 表示 | 表示 |
| 回答済み／未回答 | 表示 | 表示 | 表示 |
| 招待URL | 未使用の分だけ表示。使用済みは「使用済み」とだけ表示 | 非表示 | 非表示 |
| 専用URL | 非表示（知る手段がない） | 自分の分だけ | 非表示 |
| 最終更新日時・保存回数・有効化日時 | 非表示 | 自分の分だけ表示 | 非表示 |
| 回答内容（選択肢・条件） | 非表示 | 自分の分だけ表示 | 非表示 |
| 最終結果（参加／不参加） | 締切後に表示 | 締切後に表示 | 締切後に表示 |

最終更新日時を招待側に見せないのは、「最初は行くと答えていたが、ある人の回答後に変えた」といった推測を防ぐためです。

### 5.4 回答フォーム

- 選択肢は「行く」「行かない」「条件付きで行く」の3つ。未選択では保存できない。
- 「条件付き」を選ぶと、次の2つを設定できる。少なくとも1つは必須。
  - 人物条件：自分以外のメンバーを複数選び、「選んだ人のうち N 人以上が来るなら」を指定する。N は 1 から選んだ人数まで。N = 選んだ人数なら「全員来るなら」、N = 1 なら「誰か1人でも来るなら」になる。
  - 人数条件：「自分以外の参加者が全体で M 人以上なら」。M は 1 から「メンバー数 − 1」まで。
- 両方設定した場合は、両方を満たしたときだけ参加になる。
- フォームの下に、「回答内容は招待側を含め誰にも表示されない」「行かないと条件が合わず不参加は区別されない」と常に表示する。
- 保存後は「回答済み（最終更新：11/20 21:03、保存 3 回）」と、「このURLは 11/18 19:40 に有効化されました」を表示する。覚えのない更新に本人が気づけるようにするためです。

### 5.5 メンバーの削除と回答への影響

- 削除されたメンバーの専用URLは無効になり、その人の回答も削除する。
- 他の人の人物条件に削除された人が含まれていた場合、その人は「来ない人」として扱う。N はそのままなので、条件は満たされにくくなる。
- その場合、影響を受けた本人の回答画面に「条件に選んだ人がメンバーから外れました。回答を見直してください」と表示する。招待側には表示しない。

### 5.6 招待URLの使い捨てと再発行

招待側が知っているURLでは、本人の回答を見ることも変えることもできないようにします。

- 招待URLは1回だけ有効化できる。有効化した人にだけ専用URLを返し、サーバーには専用トークンのハッシュしか残さない。招待側も運用者も、あとから専用URLを取り出せない。
- 有効化したブラウザには専用URLを保存しておき、同じブラウザで招待URLを開き直したときは専用URLに移る。保存できない環境（一部のアプリ内ブラウザなど）では、ブックマークの案内だけを出す。
- 招待側が本人より先に招待URLを開いた場合、本人には「このURLは使用済みです」と表示される。これにより本人が不正に気づける。
- 再発行すると、古い招待URL・専用URLは無効になり、そのメンバーの回答は削除して「未回答」に戻す。回答を残すと、再発行を悪用して他人の回答を集計に使わせ続けたり、中身を探ったりできるためです。
- 再発行の確認画面に「この人の回答は削除され、もう一度回答してもらう必要があります」と表示する。
- 締め切り後は再発行できない（受付を再開すればできる）。

## 6. 集計アルゴリズム

「行く」と「条件付き」の人を全員参加と仮定し、条件を満たさない人を外す作業を変化がなくなるまで繰り返します。残った人が、条件を守ったうえで参加者が最大の組み合わせです。

### 6.1 入力と出力

- 入力：メンバー全員の一覧と、各自の回答（未回答を含む）
- 出力：参加者の集合。それ以外のメンバーはすべて「不参加」

### 6.2 手順

1. 「行く」または「条件付き」と回答した人全員を、参加候補 S に入れる。「行かない」と未回答の人は入れない。
2. S の中の条件付きの人 p を一人ずつ調べる。
   - 人物条件：p が選んだ人のうち S にいる人が N 人未満なら不成立。
   - 人数条件：S の人数から p 自身を除いて M 人未満なら不成立。
3. 不成立の人を S から外す。
4. 1人でも外したら手順 2 に戻る。誰も外れなければ終了し、S を参加者とする。

### 6.3 この方法で最大になる理由

条件はどれも「参加者が増えるほど満たしやすくなる」形だけです。そのため、条件を守れる組み合わせ同士を合わせたものも条件を守れる組み合わせになり、最大の組み合わせは必ず1つに決まります。最大の組み合わせにいる人は、手順の途中で一度も外れません。一方、残った S は全員の条件を満たしています。よって S がその最大の組み合わせと一致します。

「この人が来るなら行かない」を許すとこの性質が崩れ、最大の組み合わせが複数になりえます。そのためスコープ外にしています。

### 6.4 計算例

| ケース | 回答 | 結果 |
| --- | --- | --- |
| 互いを条件にする | A：Bが来るなら / B：Aが来るなら | A、B とも参加 |
| 条件の相手が来ない | A：Bが来るなら / B：行かない | A、B とも不参加 |
| 連鎖 | A：行く / B：AとCの2人とも来るなら / C：自分以外3人以上なら / D：Bが来るなら | 4人とも参加 |
| 連鎖が崩れる | 上と同じだが、C：自分以外4人以上なら | C が外れ、続いて B、D が外れ、A だけ参加 |

### 6.5 計算量と実行場所

- 外れる人は最大でメンバー数だけなので、繰り返しは最大でメンバー数回です。100人でも一瞬で終わります。
- 集計は必ずサーバー（Supabase のデータベース関数）で実行します。回答データをブラウザに送らないためです。
- 同じロジックを TypeScript でも実装し、両方の結果が一致することをテストで確かめます。TypeScript 版はテスト専用で、本番の画面では使いません。

## 7. データ設計（Supabase）

テーブルは5つです。すべてのテーブルで RLS（行単位のアクセス制御）を有効にし、ブラウザからの直接アクセスは全て拒否します。データに触れるのはサーバー側の API だけです。

### 7.1 構成

- 画面と API：Next.js（App Router）を Vercel に公開。API は Route Handlers で作る。
- データ：Supabase（PostgreSQL）。API からは service\_role キーで接続し、このキーはサーバーの環境変数にだけ置く。
- ブラウザには Supabase のキーを一切渡さない。
- 集計：PostgreSQL の関数 `close_room(room_id)` で実行する。

&#91;embedded content: 構成と、立場ごとに返す情報\]

ブラウザは必ず API を通り、API は立場ごとに決めた項目だけを返します。他人の回答内容を返す経路はありません。

### 7.2 テーブル

**rooms**（ルーム）

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | text | 公開用のID。推測しにくつ10文字の乱数 |
| title | text | イベント名（100文字まで） |
| deadline\_text | text | 締切の表示用テキスト（50文字まで） |
| message | text | メッセージ（500文字まで） |
| status | text | `open` または `closed` |
| admin\_token\_hash | text | 管理用トークンの SHA-256。トークンそのものは保存しない |
| created\_at | timestamptz | 作成日時 |
| closed\_at | timestamptz | 直近の締め切り日時 |
| purge\_after | timestamptz | 自動削除の予定日時。締め切りで90日後に設定する |

**members**（メンバー）

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | uuid | メンバーID |
| room\_id | text | rooms.id。ルーム削除で一緒に削除 |
| display\_name | text | 名前（50文字まで、ルーム内で重複不可） |
| invite\_token\_hash | text | 招待トークンの SHA-256。有効化の照合に使う |
| invite\_token\_enc | text | 招待トークンをサーバーの鍵で暗号化したもの。管理画面で未使用の招待URLを表示するため。有効化した瞬間に消去する |
| invite\_used\_at | timestamptz | 招待URLを有効化した日時。未使用なら null |
| member\_token\_hash | text | 専用トークンの SHA-256。未有効化なら null。専用トークンそのものはどこにも保存しない |
| sort\_order | int | 表示順 |
| created\_at | timestamptz | 追加日時 |

トークンのハッシュ列にはそれぞれ一意制約を付け、照合はハッシュの完全一致で行います。

**answers**（回答。メンバー1人につき最大1行）

| 列 | 型 | 説明 |
| --- | --- | --- |
| member\_id | uuid | 主キー。members.id。メンバー削除で一緒に削除 |
| choice | text | `yes`・`no`・`cond` のいずれか |
| cond\_people | uuid\[\] | 人物条件で選んだメンバーID。自分は含めない |
| cond\_need | int | 人物条件の N。人物条件がなければ 0 |
| cond\_min\_total | int | 人数条件の M。なければ 0 |
| updated\_at | timestamptz | 最終更新日時 |

**results**（最終結果）

| 列 | 型 | 説明 |
| --- | --- | --- |
| room\_id | text | 主キー。rooms.id |
| attending | uuid\[\] | 参加者のメンバーID |
| computed\_at | timestamptz | 集計日時 |

**audit\_events**（操作記録。回答内容は含めない）

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | bigint | 連番 |
| room\_id | text | rooms.id。ルーム削除で一緒に削除 |
| member\_id | uuid | 対象のメンバー。ルーム全体の操作なら null |
| actor | text | `admin`・`member`・`system` のいずれか |
| action | text | `member_added`・`member_removed`・`invite_reissued`・`invite_claimed`・`answer_saved`・`room_closed`・`room_reopened`・`settings_changed` |
| created\_at | timestamptz | 日時 |

回答画面の「保存回数」は、直近の `invite_claimed` 以降の `answer_saved` の件数です。操作記録はサーバーが書き込むだけで、更新・削除する API は作りません（ルームごとの自動削除を除く）。

### 7.3 制約と整合性

- `choice = 'cond'` のときは、`cond_need >= 1` か `cond_min_total >= 1` の少なくとも一方を必須にする（CHECK 制約）。
- `cond_need` は `cond_people` の人数以下にする。範囲外は API で弾く。
- `cond_people` には同じルームのメンバーだけを入れる。保存時に API とデータベース関数の両方で確かめる。
- 1ルームのメンバー数が100人を超える追加は、データベースのトリガーでも拒否する。
- 回答の保存、有効化、再発行、メンバー削除、締め切り、再開は、どれも rooms の行をロックしてから行う（`SELECT ... FOR UPDATE`）。同時に起きても順番に処理され、締め切り後の保存は拒否される。
- 有効化は「`invite_used_at` が null の行だけを更新する」条件付き更新で行い、同じ招待URLを2人が同時に開いても有効化できるのは1人だけにする。
- これらの書き込みは、操作ごとのデータベース関数にまとめ、操作記録の追加も同じトランザクションで行う。

### 7.4 RLS と権限

- 5テーブルとも RLS を有効にし、`anon` と `authenticated` 向けのポリシーは作らない（＝全て拒否）。
- さらに `anon` と `authenticated` からテーブルと関数の権限を取り上げる（`REVOKE ALL`）。設定ミスに備えた二重の守りです。
- Supabase の自動 API（PostgREST）と Realtime は使わない。

### 7.5 自動削除

- `pg_cron` で毎日 1 回、`purge_after` を過ぎたルームを削除する。メンバー・回答・結果も連動して削除される。
- 一度も締め切られないルームは、作成から 1 年で削除する。

## 8. API仕様

API は3つの系統に分かれています。管理用（`X-Admin-Token` ヘッダー）、招待用（`X-Invite-Token` ヘッダー。有効化のみ）、専用（`X-Member-Token` ヘッダー）です。どの系統でも、他人の回答内容を返す API はありません。

### 8.1 一覧

| メソッド | パス | 認証 | 用途 |
| --- | --- | --- | --- |
| POST | `/api/rooms` | なし | ルーム作成。`roomId` と管理用トークンを返す |
| GET | `/api/rooms/{roomId}/admin` | 管理用 | ルーム情報、メンバー一覧、未使用の招待トークン、回答済み／未回答、結果 |
| PATCH | `/api/rooms/{roomId}/admin` | 管理用 | イベント名・締切・メッセージの変更 |
| POST | `/api/rooms/{roomId}/members` | 管理用 | メンバー追加。招待トークンを発行して返す |
| DELETE | `/api/rooms/{roomId}/members/{memberId}` | 管理用 | メンバー削除（回答も削除） |
| POST | `/api/rooms/{roomId}/members/{memberId}/reissue` | 管理用 | 招待トークンの再発行。古い招待・専用トークンを無効にし、回答を削除する |
| POST | `/api/rooms/{roomId}/close` | 管理用 | 締め切って集計する |
| POST | `/api/rooms/{roomId}/reopen` | 管理用 | 受付を再開する。結果を削除し、回答は残す |
| POST | `/api/rooms/{roomId}/claim` | 招待用 | 招待トークンを有効化し、専用トークンを返す。使用済みなら 410 |
| GET | `/api/rooms/{roomId}/me` | 専用 | ルーム情報、メンバー一覧、回答済み／未回答、自分の回答と更新情報、結果 |
| PUT | `/api/rooms/{roomId}/me/answer` | 専用 | 自分の回答を保存する（受付中のみ） |

### 8.2 専用トークンの扱い

トークンは3種類で、それぞれ役割と保存方法が違います。専用トークンだけは、本人のブラウザ以外のどこにも残しません。

| トークン | 持つ人 | サーバーに残すもの | 寿命 |
| --- | --- | --- | --- |
| 管理用 | 招待側 | ハッシュのみ。作成時に一度だけ表示 | ルームが削除されるまで。紛失時の復旧は未決事項 #2 |
| 招待 | 招待側 → メンバー | ハッシュと暗号文。暗号文は管理画面での再表示用 | 有効化するまで。有効化した瞬間に暗号文を消し、以後は照合しても 410 |
| 専用 | メンバー本人だけ | ハッシュのみ | 再発行かメンバー削除まで |

有効化の流れは次のとおりです。

1. 招待画面が URL の `#` 以降から招待トークンを読み、`POST /claim` を呼ぶ。
2. サーバーはルームをロックし、未使用の招待トークンなら専用トークンを作る。専用トークンのハッシュを保存し、`invite_used_at` を記録し、招待トークンの暗号文を消す。
3. 専用トークンを応答で一度だけ返す。画面はそれをブラウザに保存し、`/r/{roomId}/m#{memberToken}` に移る。
4. 使用済みの場合は 410 を返す。画面は、ブラウザに専用トークンが保存されていれば回答画面へ、なければ「使用済み」の案内へ移る。

### 8.3 主なレスポンス

`GET /api/rooms/{roomId}/me` の例：

```json
{
  "room": { "title": "太郎＆花子 結婚式", "deadlineText": "12月20日", "message": "…", "status": "open" },
  "members": [
    { "id": "…", "name": "佐藤", "answered": true },
    { "id": "…", "name": "鈴木", "answered": false }
  ],
  "me": {
    "id": "…",
    "answer": { "choice": "cond", "condPeople": ["…"], "condNeed": 1, "condMinTotal": 0, "updatedAt": "2026-11-20T12:03:00Z" },
    "saveCount": 3,
    "claimedAt": "2026-11-18T10:40:00Z",
    "conditionNotice": false
  },
  "result": null
}
```

- `result` は `status = closed` のときだけ `{ "attending": [memberId, …], "computedAt": … }` が入る。不参加の理由は含めない。
- `conditionNotice` は、自分の人物条件に削除済みのメンバーが含まれているとき `true` になる（5.5）。
- `saveCount` と `claimedAt` は、覚えのない操作に本人が気づくための情報。本人にしか返さない。
- 管理用の GET は `me` を返さない。各メンバーには `answered` と、未使用なら招待トークン、使用済みなら `inviteUsed: true` だけを付ける。専用トークンは返せない（サーバーにもない）。

### 8.4 入力チェックとエラー

| ケース | HTTP | 内容 |
| --- | --- | --- |
| トークンがない・一致しない・別ルームのもの | 404 | ルームが存在しない場合と区別しない |
| パスの memberId がそのルームのメンバーではない | 404 | 他ルームのメンバーの存在も明かさない |
| 使用済みの招待トークン | 410 | 「このURLは使用済みです」 |
| 締め切り後の回答保存・再発行 | 409 | 「受付は終了しました」 |
| 条件が不正（自分を選んだ、N が範囲外、他ルームのID、条件なし） | 422 | 項目ごとのエラー |
| 定義にない項目を送った | 422 | 無視せず拒否する |
| メンバー数が上限を超える | 422 | 「メンバーは100人までです」 |
| 回数制限を超えた | 429 | 時間をおいて再試行 |
| 文字数オーバー・重複した名前 | 422 | 項目ごとのエラー |

### 8.5 回数制限

- ルーム作成：同じ接続元から 1 時間に 10 件まで
- 回答保存：同じトークンで 1 分に 10 回まで
- トークンを照合する API 全般：同じ接続元から 1 分に 60 回まで

### 8.6 権限チェックの原則

すべての API は、処理の前に次の順で確かめます。どれか1つでも合わなければ、何も変更せずに拒否します。

1. **トークンの種類がその API 用か。** 管理用 API に専用トークンを送っても通らない。逆も同じ。
2. **トークンがパスの roomId のルームのものか。** トークンからルームを引いて、パスと一致するかを見る。
3. **操作対象がそのルームのものか。** パスの memberId、条件のメンバーIDは、すべて `room_id` を含めた条件で検索する。ID だけでは検索しない。
4. **ルームの状態で許される操作か。** 締切済みなら回答保存・再発行・メンバーの追加と削除を拒否する。

あわせて、次のルールを守ります。

- **誰のデータを書くかはトークンで決める。** 回答保存では、本文に memberId を含めさせない。専用トークンから本人を特定する。
- **サーバーが決める値は受け取らない。** 更新日時、ルームの状態、最終結果、操作記録はサーバーだけが設定する。入力スキーマにない項目が来たら 422 で拒否する。
- **最終結果を書くのは集計関数だけ。** 結果を直接書き換える API は作らない。ルームの状態を変えるのも「締め切る」「再開する」の2つだけ。
- **すべての変更を操作記録に残す。** 変更と記録は同じトランザクションで行い、片方だけが残ることがないようにする。
- **全 API で共通の認可処理を使う。** 各 API が個別に書かず、「トークンの種類と roomId を受け取り、検証済みのルームとメンバーを返す」関数を必ず通す。通し忘れはテストで検出する（10.1）。

## 9. セキュリティとプライバシー

回答内容がサーバーの外に出るのは、本人のブラウザに自分の分を返すときだけです。それ以外の対策は、「不正に本人が気づける」ことを中心にします。

### 9.1 対策一覧

| リスク | 対策 |
| --- | --- |
| 招待側が管理画面で回答内容を見る | 管理用 API は回答済み／未回答しか返さない。集計はサーバーで行う |
| 招待側が本人のURLを使って回答を見る・書き換える | 招待URLは使い捨て。専用URLは本人にしか発行せず、サーバーにもハッシュしか残さない（5.6） |
| 招待側が本人より先に招待URLを開く | 本人に「使用済み」と表示され、不正に気づける |
| 招待側が再発行を悪用する | 再発行で回答を削除する。中身を引き継がないので探れない。本人の専用URLが無効になるので本人も気づける |
| 招待側が更新のタイミングから推測する | 最終更新日時と保存回数は本人にしか返さない |
| 他ルームのデータを操作する | トークンと操作対象が同じルームかを全 API 共通の処理で確認する（8.6） |
| 送信値を書き換えて他人の回答や日時・結果を改竄する | 本人はトークンで決め、更新日時・状態・結果・記録はサーバーだけが書く。未定義の項目は拒否 |
| 同時操作で不整合が起きる | 書き込みはルーム単位でロックし、有効化は条件付き更新で一度きりにする |
| ブラウザから Supabase を直接叩かれる | ブラウザにキーを渡さない。RLS と REVOKE で二重に拒否 |
| サーバー専用のキーが画面のコードに混ざる | Supabase を扱うコードに `server-only` を付け、ブラウザ向けに読み込むとビルドが失敗するようにする。環境変数に `NEXT_PUBLIC_` を付けない |
| 他人の専用URLで成りすます | 回答済み表示、最終更新日時、保存回数で本人が気づける。招待側に再発行してもらえる |
| トークンの総当たり | 128ビット以上の乱数、照合失敗は全て 404、接続元ごとの回数制限 |
| URL がログやリファラーに残る | トークンは `#` 以降に置き、ヘッダーで送る。`Referrer-Policy: no-referrer` を付ける |
| データベースの流出 | トークンはハッシュと暗号文でしか持たない。締め切りから90日で自動削除 |
| 運用者が誤って回答を見る | 本番のデータは障害対応以外で開かない。開発とテストは別の Supabase プロジェクトで行う |
| 画面への不正な文字列の埋め込み | 名前やメッセージは常にテキストとして表示し、HTML として解釈しない |

招待側が架空のメンバーを加えて結果の変化を探ることは、仕組みでは防ぎません。メンバー一覧を全員に見せることで、不自然な人に気づけるようにします（前提どおり、招待側にそこまでする動機はないと考えます）。

### 9.2 利用者への説明

- 回答画面と利用規約に、「回答内容は招待側を含め他の利用者には表示されない」「サービス運用者は障害対応以外では閲覧しない」「最終結果から回答が推測される場合がある」と明記する。
- プライバシーポリシーに、保存する情報（名前、回答、接続元の回数制限に使う情報）、保持期間、削除の依頼方法を書く。
- 名前はニックネームでもよいと案内し、本名の入力を求めない。
